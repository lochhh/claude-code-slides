Here are the top 5 things new Claude Code users need to know about prompting, based on the Claude Code best practice guide in comments: 1️⃣ Be explicit - Claude does what you say, not what you might mean Claude 4.x models follow instructions precisely. If you say “can you suggest some changes,” it may only suggest rather than implement. Say “make these changes” or “implement this” when you want action. For proactive behaviour by default, add to your prompts: > “Default to implementing changes rather than only suggesting them. If intent is unclear, infer the most useful action and proceed.” 2️⃣Add context for why, not just what Explaining the reasoning behind your request helps Claude generalise better. Instead of just stating a rule, give the motivation: ❌ “Use 2-space indentation” ✅ “Use 2-space indentation because our codebase follows Google’s style guide and consistency matters for code reviews” Claude can then apply that reasoning to related decisions you haven’t explicitly covered. 3️⃣ Tell Claude to explore code before proposing solutions Without prompting, Claude can be overly confident and propose fixes without actually reading the relevant files. Add explicit guidance: > “ALWAYS read and understand relevant files before proposing code edits. Do not speculate about code you have not inspected. If I reference a specific file, you MUST open and inspect it before explaining or proposing fixes.” This dramatically reduces hallucinated solutions. 4️⃣ Control verbosity and formatting explicitly Claude 4.x tends toward efficiency - it may skip summaries after tool calls and jump straight to the next action. If you want visibility: > “After completing a task involving tool use, provide a quick summary of the work you’ve done.” For output formatting (avoiding excessive markdown/bullet points), tell Claude what to do rather than what not to do: > “Write in clear, flowing prose paragraphs. Reserve markdown for code blocks and simple headings only.” 5️⃣ Use state tracking for longer tasks Claude Code excels at long-horizon work across multiple context windows. Help it by: - Having it write tests first in a structured format (e.g. `[tests.json](http://tests.json?trk=public_post-text)`) - Creating setup scripts like `init. sh` for repeatable environment setup - Using git commits as checkpoints - Prompting: “Keep track of your progress in a progress notes file. Focus on incremental work and commit frequently.” This lets Claude pick up exactly where it left off when context refreshes.

  If you’re still relying on clicks for things the terminal can do faster, you’re choosing comfort over efficiency. Linux commands aren’t optional for developers — they’re leverage. Below are 10 Linux commands + real developer context that actually save time. Each one includes why it matters and exact usage 1. touch – Create multiple files instantly Problem: Creating files one-by-one in VS Code is slow and pointless. Why this works: One command, many files, zero clicks. touch [index.html](http://index.html?trk=public_post-text) [style.css](http://style.css?trk=public_post-text) [app.js](http://app.js?trk=public_post-text) [README.md](https://www.linkedin.com/redir/redirect?url=http%3A%2F%2FREADME%2Emd&urlhash=JPtp&trk=public_post-text) Actionable use: Use this when bootstrapping projects or components. --- 2. mkdir -p – Create nested folders in one go Problem: Manually creating folder trees is wasted effort. Why this works: Builds full structure instantly. mkdir -p src/components/Header src/components/Footer src/utils Actionable use: Use this for React, backend APIs, or clean project architecture. --- 3. alias – Shorten painful commands Problem: Re-typing long Git commands is dumb. Why this works: One word replaces repetitive commands. alias gs="git status" alias gc="git commit -m" alias gp="git push" Actionable use: Add these to ~/.bashrc or ~/.zshrc. --- 4. grep – Find anything, fast Problem: Searching files manually doesn’t scale. Why this works: Instantly locates text across files. grep -R "useEffect" src/ Actionable use: Debug, refactor, or audit codebases. --- 5. find – Locate files without guessing Problem: Forgetting file locations wastes time. Why this works: Finds files by name, type, or extension. find . -name "\*.js" Actionable use: Large projects, monorepos, legacy code. --- 6. chmod – Fix permission issues immediately Problem: “Permission denied” errors block work. Why this works: One command fixes execution issues. chmod +x [script.sh](https://www.linkedin.com/redir/redirect?url=http%3A%2F%2Fscript%2Esh&urlhash=6MsU&trk=public_post-text) Actionable use: Shell scripts, deployment scripts, CI tasks. --- 7. history | grep – Reuse past commands Problem: Forgetting useful commands is common.
