I've been figuring out how to manage context when building with Claude Code. Still experimenting. If you're not careful, the context window runs out of space, the quality drops for a bit, then the context auto-compacts and you're never quite sure what's been lost. I'm combining a few approaches for managing context at the moment, and seeing what works. DOCUMENTATION AS CONTEXT I create "documentation as context" in each repo. Technically, I get Claude to create it! I've found this very useful for ensuring Claude has access to consistent context and references as needed. Inspired by [https://lnkd.in/eQAFHdgg](https://www.linkedin.com/redir/redirect?url=https%3A%2F%2Flnkd%2Ein%2FeQAFHdgg&urlhash=2_8e&trk=public_post-text) - thanks [André Figueira](https://uk.linkedin.com/in/andrefigueira?trk=public_post-text) This is particularly good for describing the architecture and coding patterns in your repo, design guidelines, database schemas, auth flows etc. By breaking it down into a bunch of small files, you can easily feed Claude the context it needs for a particular task. Or it can search for it and feed itself of course. Breaking it all down like this really adds to the utility of the next two approaches. PHASED-BASED SESSIONS Where appropriate I break work down into phases, and either clear Claude context or start a new session when starting a new phase. I find this more efficient than compacting the conversation when changing focus. My aim is to break work down into tasks that can be completed within a single context window. I'm a bit hit and miss with this, but slowly improving over time. The next approach also helps... SUB-AGENTS I've been experimenting with subagents as a way to separate task-specific context from the context of the main thread. Mixed results so far, it seems to depend greatly on the types of task. The main downside is that you can't see what's going on so much, especially if you run several concurrently. So I'm currently mainly using this for token-heavy operations that have pretty good guardrails, and I'm more interested in the outcome than the minutiae of the back-and-forth. One of my favourite commands is along the lines of "kick off 5 test-engineer subagents to create the unit and integration tests for XYZ feature". It goes off, divides the work between 5 agents, who then munch a load of tokens, write the tests and test the test, and finally let the main thread (and me) know how they all got on. Who else has been using any of these approaches? What has your experience been? What else should I try?

Great to see you getting so much use out of the methodology Simon. For others following along: the core idea is treating documentation as the primary control mechanism for AI output quality. When you give an LLM vague or missing context, you get variable results. When you give it structured context that constrains the solution space (architectural decisions, coding standards, domain models, explicit boundaries) outputs converge toward intended behaviour. I call this "context substrate." Machine-parseable knowledge that AI can synthesise on demand into whatever view you need at that moment. The phased sessions approach you're describing maps directly to this. Each phase gets a clean context window with precisely the substrate it needs. No accumulated noise from previous tasks. No hoping the compactor kept the right things. The subagent pattern is interesting for the same reason. You're essentially scoping context per task type. The test-engineer swarm works because testing has clear boundaries and success criteria. The substrate constrains what "good" looks like. What I'm finding is that teams who invest in building good substrate upfront spend far less time fighting context limits downstream.
